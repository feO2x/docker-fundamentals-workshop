# Root AGENTS.md

This repo contains all assets for my Docker Fundamentals workshop that I give at TELIS/GWVS. This workshop is aimed at beginners and builds on my Linux Fundamentals workshop (`~/Code/linux-fundamentals-workshop`), which serves as the blueprint for this repo.

## General

- When committing, sign off and use a Conventional Commits message. Decide whether a message body should be included depending on the changes.
- Usually, `npm run dev` is running, so you can access http://localhost:5173/ without starting your own server. 

## Feedback Loops

Install dependencies with `npm ci` before running these commands.

- `npm run lint`: lints `src/` with oxlint (React, TypeScript, and oxc rules from `.oxlintrc.json`).
- `npm run build`: type-checks the project with `tsc -b` and builds the production bundle into `dist/` with Vite.
- `npm run format:check`: checks formatting with Prettier. Use `npm run format` to fix formatting issues.

CI (`.github/workflows/ci.yml`) runs these commands on pull requests, `.github/workflows/deploy.yml` runs them before deploying to GitHub Pages.

## Good to know

- The slides (`slides.html`, `src/slides/`) use the reveal.js setup of the Linux Fundamentals workshop: one vertical `BlockStack` per agenda block with its `SectionSlide` on top, `navigationMode: 'linear'`, and a separate Vite entry so Reveal and highlight.js stay out of the agenda bundle. Its pitfalls apply here as well. Fragments that follow a multi-step `StepCode` belong inside `WhenDeckReady`, otherwise they appear before the code steps. `BlockStack` sets `data-start-indexv="0"` so → always enters a block at its section slide. `slides.html?transition=none` is handy for screenshots. Fragments inside `WhenDeckReady` stay hidden with `fragments=false`.
- `StepCode` highlights one line per step by default. `steps={false}` shows all lines at once, e.g. for commands on an exercise slide.
- The "Warum Docker?" slides use floating tags of official images (`src/slides/images.ts`). The versions and `/etc/os-release` values on the slides were read from the registries on 2026-11-07: `python:3.12` is 3.12.16 and `python:3.13` is 3.13.18, both on Debian 13 (trixie). `mcr.microsoft.com/dotnet/sdk:10.0` is Ubuntu 24.04.5 LTS (since .NET 10, Microsoft's default images are Ubuntu-based), starts `/bin/bash`, sets `DOTNET_NOLOGO=true` and is about 350 MB compressed. The layer slide in the concepts block lists the seven `linux/amd64` layers of `python:3.12` with IDs and compressed sizes from the Docker Hub manifests (2026-11-09); the lower four are identical in `python:3.13`. Re-check them before each workshop.
- The push exercises use a local `registry:2` container instead of the internal Harbor registry, because not every attendee can reach Harbor. It listens on host port 5050 (`REGISTRY_RUN` in `src/slides/images.ts`), because the AirPlay receiver occupies port 5000 on macOS.
- `.github/workflows/exercises.yml` plays every exercise through on a GitHub runner, and the sample outputs on the slides (`docker ps`, `docker logs`, `docker history`, cache hits, build times, image sizes from Docker 29's `docker image ls` with `DISK USAGE`/`CONTENT SIZE`) come from its logs. When an exercise changes, update the workflow and take the outputs from its next run. Since 2026-11-11 the machine the slides are written on has Docker Desktop (Apple Silicon), handy for trying things out, but image sizes on the slides stay the `linux/amd64` values from CI. The slides import the Dockerfiles and compose files from `exercises/` with `?raw` (`src/slides/dockerfile.ts` strips lines starting with `#`, indented YAML comments stay), so they always show the tested files.
- When running the workflow's final exercise steps locally, commit first: they copy the solution into `exercises/zaehler` and end with `git checkout`, which overwrites uncommitted changes there.
- On 2026-11-07, all exercises were also played through on Docker Desktop 29.9.2 (Windows, WSL 2 backend, containerd image store), partly from PowerShell after a `git clone` with Git for Windows (`core.autocrlf=true`). Results: the outputs match the CI runner apart from build times (the caching slides show the Docker Desktop values), `.gitattributes` keeps the scripts at LF, `"${PWD}/…"` bind mounts work in PowerShell, umlauts typed in PowerShell reach the container (`wetter Bad Tölz`), `--platform linux/arm64` runs under emulation, and `localhost:5050`/`8080` are reachable from Windows. A `.ps1` without BOM garbles umlauts in Windows PowerShell 5.1, which matters only when scripting such a check.
- .NET 10 has no Debian images (only previews had `trixie-slim`). The runtime variants on the base image slide are Ubuntu (default), Alpine and `noble-chiseled`.
- The Docker Compose block has no exercise. Its example is `exercises/datenbank/compose.yaml` (Adminer and `postgres:18`); Adminer suggests `db` as server, which shows the service name as hostname. The network slide still uses the `wetter` → `registry` demo from the registry block.
- The final exercise is the repair variant with Docker Compose: a counter (ASP.NET Core with Npgsql) and `postgres:18`. `exercises/zaehler/Dockerfile` and `compose.yaml` are broken on purpose with six faults: single stage on the SDK, `COPY . .` before restore, no `USER`, `Host=localhost` in the connection string, a plain `depends_on` without health check, and no volume for the database. `exercises/loesungen/zaehler.Dockerfile` and `zaehler.compose.yaml` are the fix; the latter also sets `image: localhost:5050/zaehler:1.0` for the optional `docker compose push`.
- The app creates its table at startup and exits with code 1 and a single line (`Keine Verbindung zur Datenbank: …`) if Postgres isn't reachable. It must not throw instead: as PID 1 in a container, .NET 10 hung at 100 % CPU after an unhandled exception (seen on Docker Desktop, arm64) instead of exiting. Postgres needs about 0.6 s for initdb on the first start, which was enough for the app to fail 5 out of 5 times without `condition: service_healthy`; with an existing volume the race doesn't show, hence the `down -v` acceptance criterion. `GssEncryptionMode.Disable` keeps Npgsql from logging a missing `libgssapi_krb5.so.2`.
- Postgres 18 stores its data under `/var/lib/postgresql/18/docker`; the volume belongs at `/var/lib/postgresql`. A volume at the old `/var/lib/postgresql/data` makes the container exit with `in 18+, these Docker images are configured …`, and Compose reports `dependency failed to start`. The health check uses `pg_isready -h localhost`: without `-h`, it asks via the Unix socket and reports ready while the temporary initdb server is running (measured 2026-11-11).
- From the Dockerfile block on, every Dockerfile sets a non-root `USER`, building on the Linux Fundamentals users block: `USER ubuntu` (UID 1000, shipped with `ubuntu:24.04`) and `USER $APP_UID` (`app`, UID 1654, shipped with the .NET images; chiseled images set it themselves). `USER` adds no BuildKit step, so the `[n/4]` numbers on the caching slides stay the same.
- Bind mounts on the slides use `"${PWD}/…"`, which works in both Bash and PowerShell. `.gitattributes` keeps scripts and Dockerfiles at LF, because CRLF from a Windows checkout breaks them in the container.
